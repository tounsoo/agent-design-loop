# @agent-design-loop/harness

The harness is the checks that hold an agent's UI work to rules a product keeps in the repo as data. Each check reads one product's inventories from that product's `harness.config.ts` and exits non-zero when the UI breaks a rule. The harness also holds its own tests, in `fixtures/`, and the page [How this design loop works](docs/how-it-works.md), which explains the control ladder, each check, and when a proposal is required.

| Path | What it is |
| --- | --- |
| `src/` | One file per check, run as an npm script from the repository root |
| `src/lib/` | What the checks share: config loading (`config.ts`), the config types and parser (`parse-config.ts`), the adapter, page scope, and path search |
| `fixtures/` | The harness's own tests: a fixture product, legal cases, and known-bad shapes in `fixtures/illegal/` |
| `index.ts` | The package entry, `@agent-design-loop/harness` |
| `docs/how-it-works.md` | The walkthrough |

Two products use it in this repository: [Meridian](../../products/meridian/README.md), an accounts-payable workspace, and Nook, a room booking app under `products/nook/`.

## Run the checks

```sh
npm run check:fixtures && npm run check
```

`check:fixtures` runs the harness's own tests. `fixtures/product/` is a small product with its own `harness.config.ts` that every check passes. Each folder beside it, and each one under `fixtures/illegal/`, has a `case.ts` that changes some of that config's paths and names the checks to run, with the phrase each must print. The run exits 0 only when the illegal cases fail and the legal ones pass: the fixture product, the stand-in design system in `fixtures/fake-ds/`, and small products of their own (`fixtures/two-tasks/`, `fixtures/two-collection-pages/`, `fixtures/own-sections/`) that show a rule reads its product's config and inputs, not Meridian's. `fixtures/opt-out/` and the `fixtures/illegal/opt-out-*` cases test `check:opt-outs`, the retirement threshold has Vitest tests in `src/lib/opt-outs.test.ts`, the design loop graph has them in `src/lib/loop.test.ts`, and the loop trace has them in `src/lib/trace.test.ts`. A case that sets `base` can also give `proposals` and `baseProposals`, two folders of proposal files that `check:inventories` reads as the change's proposals and the base's, matched by file name. Thirteen cases build an `index.html`, their own or another case's, and open it, so like `check:target-size` and `check:accessible-names` they need Chrome: `fixtures/target-size-whole-document/`, `fixtures/illegal/small-control-outside-page/` and `fixtures/illegal/small-control-in-closed-menu/` measure it, and `fixtures/announced-progress/`, `fixtures/announced-sort/`, `fixtures/announced-waitlist/`, `fixtures/listed-press-gap/`, `fixtures/illegal/step-read-as-in-progress/`, `fixtures/illegal/undeclared-current-step/`, `fixtures/illegal/unnamed-control/`, `fixtures/illegal/waitlist-row-loses-focus/`, `fixtures/illegal/silent-waitlist-leave/` and `fixtures/illegal/stale-press-gap/` read what a screen reader hears. `illegal/step-read-as-in-progress` is Meridian's pull request 32 before its fix, Todae's `Steps` reading a waiting stage as "In progress", and `announced-progress` is the same list fixed. `illegal/waitlist-row-loses-focus` is Nook's Waitlist rows from pull request 42 before its fix, where joining swapped the row's button and dropped focus, `illegal/silent-waitlist-leave` is the same page halfway fixed, where leaving while a room was free said nothing, and `announced-waitlist` is the page fixed. `listed-press-gap` lists the silent leave in `knownGaps` and passes, and `illegal/stale-press-gap` still lists it on the fixed page and fails. `announced-sort` reorders a list and says so through Todae's announcer, which writes 100 ms after the press, so it fails if the check reads the page too soon. `npm run check:fixtures -- illegal/two-primaries` runs one case.

`check` is the build gate. It runs `typecheck`, `lint`, and `test` once for the whole repository, then `check:meridian` and `check:nook`, then `check:proposals`, `check:retirement` and `check:loop`. Each of the two product scripts runs `check:product` on one product's config.

| Command | What it fails |
| --- | --- |
| `npm run typecheck` | A modeled state with no exhaustive view, and ordinary type errors |
| `npm run lint` | ESLint |
| `npm run test` | The Vitest suite of every product. Meridian's covers the flow, the two-step journey, the request-changes branch, and the rendered states |

The rule checks read one product. `check:rules` lists them, in this order, and each needs `--config <file>`:

| Command | What it fails |
| --- | --- |
| `npm run lint:product-ui` | Off-catalog UI, including an import from another product's directories. Re-exports (`export ... from`), `import()`, `require()` (also as `globalThis.require` or `(0, require)`), and `import x = require()` count as imports, and so does Vite's `import.meta.glob`. A dynamic load whose specifier is not a string literal fails because it cannot be checked, and so does `require` held under another name. A loader made with `createRequire` is not read |
| `npm run lint:slots` | The primary-slot contract: a page type named in `shells.primarySlots` whose slot does not hold exactly one primary action, or a slot name the page type's shell does not define |
| `npm run check:step-budget` | A task path longer than that task's `max_steps`, or any longer route to the same success over it: a route takes the steps a task graph in the same flow names, in any order and each at most once, then finishes the shortest way. Also a task graph and shipped reducer whose shortest paths differ, or a task in `tasks` with no graph mapped under `flows[].tasks` in the product's `harness.config.ts`. Every task is measured. A flow state is named by its `status` field, or by `flowStatus(state)` when the graph module exports one; a state the search meets with neither fails |
| `npm run check:disclosure` | Disclosure depth or count above the cap |
| `npm run check:priority` | Per page: more than one primary action, a primary that is not the rank-1 action in `priority` (Meridian's Approve), the rank-2 action shown as primary or more than once (Meridian's Request changes), a primary inside a disclosure, or an action button whose variant is computed. Across the product: no page with the rank-1 primary, a rank-1 or rank-2 button no page reaches, or a section in `disclosed_sections` that is not behind a disclosure |
| `npm run check:one-thing` | Per page: a page rendered inside another page, a primary on a collection page, or more visible questions than the cap. Also a page type that renders no page. A product may render a page type as often as it needs. Page-type membership is `allowed_page_types`, which this check reads |
| `npm run check:inventories` | A chrome layout, content layout, or page type outside the allowlists; a collection body that is not a registered content layout; or an inventory-set change versus the pull request base that no adopted proposal lists. A proposal covers a change when it is `status: decided` on the base, `status: adopted` in the change, and its `changes` on the base list, exactly, what changed: the member added or removed, the constant, the config field or its new value, each changed string in `flows`, `adapter.<field>` for an adapter field, the new adapter path, or the product's directory. A proposal the change adds covers nothing, unless it only adds: a change that only adds members to the catalog exports, `allowed_layouts`, `allowed_content_layouts` or the flow states passes with a proposal the change adds as `status: adopted` that lists them under `adds` and nothing else, that is not on the base, that lists no name a base proposal already lists under `adds`, and that names nothing the change removes or changes otherwise. A product the base does not have at all, such as a new one under `products/`, is such a change. A new page type is never an addition: it also needs an entry under `shells` in the config, so a decided proposal lists both ([proposal 2026-11-12-page-types-take-two-pull-requests](../../proposals/2026-11-12-page-types-take-two-pull-requests.md)). A product that moved is compared with the base at its old paths, so its config path changes need a proposal. A list the base does not export yet may be recorded once: `allowed_layouts`, `allowed_content_layouts` or `disclosed_sections`. That bootstrap covered the first two, and it covers the design system adapter the config names. A base exports a list when it declares it with `export const` or names a local `const` in an export clause; a base file with `export *` or `export =` that does not export the list by name fails the check. A config file the base does not have is a change, so a renamed config needs a proposal |
| `npm run check:state-coverage` | A modeled flow state with no view |
| `npm run check:target-size` | A control under WCAG 2.5.8 (24 CSS px), spacing exception included, anywhere in the document on any modeled state: the page and the chrome around it, with each closed disclosure opened on its own. It opens every state in `modeledStates`: bare, or once per query string that `flows[].previews` in the product's `harness.config.ts` lists for it. Needs a headless Chrome, and names what to install when there is none; `--list` prints the previews without it. |
| `npm run check:accessible-names` | On the same previews, read from Chrome's accessibility tree: a control with no accessible name; an announcement the flow's `accessible-names.ts` declares for a preview that a screen reader does not hear there, compared by role, name or text, and any states it gives; a node whose announcement changes with the state, one with `aria-current`, which its entry must give as `current`, a live region, by role or `aria-live`, with something to say, or any progress bar or meter, that the file leaves out; and a preview the file declares nothing for, or a key that is not a preview. Then, pressing each action on each preview from a fresh load: a press that changes what a screen reader could read while no live region says anything new, focus stays put and the control's own state stays the same, and a press that leaves focus on the page body, unless the file's `knownGaps` lists it; and a `knownGaps` entry whose press no longer has its problem. The file sits beside the flow's `views` module and exports `accessibleNames`, typed `satisfies AccessibleNames`, and optionally `knownGaps`, typed `satisfies KnownGaps`, each entry with `fixIn`, the issue, pull request or proposal its fix waits on; an entry without one fails. Needs a headless Chrome; `--list` checks the file against the previews without it |

There is no LLM judge on CI.

Five more checks guard the rules, the proposals and the loop themselves. None is in `check:rules`, and a product cannot opt out of any.

| Command | What it fails |
| --- | --- |
| `npm run check:opt-outs` | Needs `--config`. An entry in the config's `optOuts` that names a rule `check:rules` does not run, a core rule (`lint:product-ui` or `check:inventories`), or a proposal that is missing, is not directly in `paths.proposals`, is not `status: adopted`, or has no `opts-out` entry naming the rule and the product's `paths.source`. `check:product` runs it before any rule check |
| `npm run check:proposals` | Takes no flags. Reads every proposal in `proposals/` and in each product config's `paths.proposals`, `README.md` aside. Fails a proposal without front matter, with an unknown or missing `status` or `changes`, a field that is not a list, `adds` beside `changes`, `retires` or `opts-out` or on a proposal that is not `adopted`, an `opts-out` entry that is not `<rule> for <paths.source>`, an empty or missing `## Reason`, `## Preview` or `## Adoption`, the names before the rename (`status: graduated`, `## Graduation`, which still count on the base), or a `## States` section that misses an edge case (Empty, Loading, Error, Long content, Permissions, Over time), gives a state no text, marks one out of scope without a reason, lists only edge cases, or puts `None` beside other states. Compared with the pull request base, it fails a status that moves more than one step (`open`, `decided`, `adopted`) or backwards, a change to a decided or adopted proposal's `changes`, `retires`, `opts-out` or `adds`, a decided or adopted proposal renamed or deleted, a new proposal that starts as `adopted` while it lists anything to change under `changes`, `retires` or `opts-out`, a proposal that lists anything under `changes` or `adds` with no `## States` when it is new or moves from `open` to `decided`, a decided or adopted proposal that drops the `## States` it had, and a proposal the change adds or renames whose file name is not a real date no later than tomorrow in UTC, the day it was written, and a lowercase slug, such as `2026-11-12-side-panel.md`, or that shares its name with a proposal in another proposal folder |
| `npm run check:retirement` | Takes no flags. Reads every `harness.config.ts` git knows of outside this package, tracked or new. Fails when two configs name the same `paths.source`, when any product's opt-outs fail the rules of `check:opt-outs`, and when a majority of products, and at least two, opt out of the same rule. With two products, both must opt out. Compared with the pull request base, it also fails a rule that leaves `check:rules` unless an adopted proposal lists it under `retires`, and a new opt-out unless its proposal is adopted in the change and listed it under `opts-out` when it was decided |
| `npm run check:loop` | Takes no `--config`. Fails when the design loop graph in `design-loop.ts` is not one an agent can follow: a dangling edge, an unreachable node, an eval node naming a script `package.json` lacks or with no retry on `fail`, a human gate with no `CODEOWNERS` owner, or an end the run can reach without an eval node passing after the last change. Also fails when the diagram in `docs/how-it-works.md` is not the one the graph draws. `--write` redraws it |
| `npm run check:trace` | Takes no flags. Reads the change against its base, as `check:inventories` does. Fails when the change touches a product's directory and adds no loop trace under `traces/` at the repository root, and when a trace the change adds or edits does not start at the graph's `start`, steps between nodes no edge connects, gives a router, eval or human step no `when` or one its edges lack, stops anywhere but a checkpoint, or ends its run with a change to checked state that no passing eval node follows. A run paused at a checkpoint with an edge out may stop unchecked. A file under `traces/` that is not a `.jsonl` trace or the folder's README fails too. It is not in `check`, because the agent runs the gate in the middle of its walk. CI runs it after `check:loop`. `npm run loop:step -- traces/<change>.jsonl <node> [when]` appends a step and refuses one the graph does not allow. A trace is the agent's own record, so passing shows the record is a walk the graph allows, not that the work was done |

### Check one product

```sh
npm run check:product -- --config products/nook/harness.config.ts
```

`check:product` runs `check:opt-outs`, then every check in `check:rules` against that config, in the same order, and stops at the first failure. It skips a rule the config opts out of, and says so. It reads the list from `package.json`, so the two cannot drift. `npm run check:meridian` and `npm run check:nook` call it with their product's config.

A check reads its paths only from the config that `--config <file>` names. There is no config at the repository root, so a rule check run without `--config` exits with "give the product's config". Besides `--config`, `check:inventories` reads `--base <file>`, and `--proposals <dir>` and `--base-proposals <dir>`, which need `--base`, and `check:target-size` and `check:accessible-names` read `--list`. `npm run screenshots`, which is not a check, reads `--out <dir>`, `--state <name>` and `--base <ref>`, or `--pin <dir>` with no other flag but `--config`. Any other flag, and any `--name=<value>` form, is refused, so a stale invocation cannot pass on the wrong product.

`check:target-size` builds the directory in `paths.web`, serves it with `vite preview` on port 4173, and measures every control in the document in headless Chrome, not only those inside the `[data-page]` element. It finds Chrome at `CHROME_PATH`, then the chrome-headless-shell that `npm run setup:chrome` installs into `.cache/chrome`, the build this repository's `puppeteer-core` pins, then the usual `/usr/bin` paths. CI runs `npm run setup:chrome` too, so both measure in the same build. With no Chrome, the check names each place it looked and both fixes.

`check:accessible-names` builds and serves the app the same way, in the same Chrome. On each preview it reads the whole document's accessibility tree, the one a screen reader reads, through the DevTools protocol: each node's role, its accessible name, the text its subtree reads with `aria-hidden` runs left out, and `aria-current`, disabled, expanded, checked, pressed and selected. It reads each preview as it loads, so it does not open disclosures or wait for a live region to fill. Declare what changes between states, not the whole tree: a snapshot of everything turns every change into a diff nobody reads. Roles are Chrome's names, such as `image` and `DisclosureTriangle`. A node's text is its runs joined by a space, since the tree does not say which runs share a line, so write it the way a failure message prints it. Frames inside the page are not read. [Proposal 2026-11-11-accessible-names-per-state](../../proposals/2026-11-11-accessible-names-per-state.md) records the rule.

Then it presses every action. On each preview it takes each enabled button, link, disclosure summary, menu item, tab, checkbox, radio or switch in the tree, reloads the preview with the origin's storage cleared, focuses that control, checks that focus stayed on it, presses Enter, or Space for a checkbox, radio, switch, or checkbox or radio menu item, and reads the page 150 ms later, past the 100 ms Todae's announcer waits before it writes its live region (inside an open Todae modal it writes later, which the check does not wait for). If the tree a screen reader reads changed, the press must have told it: a live region that was on the page before the press says something new, or an alert appears with something to say; focus moves to another element; or focus stays on the control and its expanded, checked, pressed or selected state changes. A new name on the focused control is not enough, and neither is a status region added with its words already in it, since screen readers do not reliably read either. Focus on the page body after a press fails too, whether or not anything else changed. A press that loads another document is skipped and not counted, and a dialog a press opens is dismissed. Problems a product has not fixed yet go in `knownGaps` beside the declarations, as `{ presses: ['button "Try again"'], problem: "focus lost", previews: ["state=error"], why, fixIn }`, and the check's last line counts them. `fixIn` is where the fix is tracked: a GitHub issue or pull request URL, or the path of a proposal file, which must exist. An entry without it fails, with or without Chrome, so no gap waits on nothing. Leaving `previews` out covers every preview, later ones included. An entry whose press no longer has its problem on a preview it names fails, so fixes take entries off the list. Pressing costs time, about a third of a second a press: Meridian's 112 presses take its run from about 15 to about 49 seconds, and Nook's 35 from about 15 to about 22. [Proposal 2026-11-12-press-every-action](../../proposals/2026-11-12-press-every-action.md) records it, and [proposal 2026-11-12-shell-owned-focus](../../proposals/2026-11-12-shell-owned-focus.md) adds `fixIn`.

`check:inventories` and `check:trace` compare with `INVENTORY_BASE` when it is set. CI sets it to the pull request base, or on a push to `main` to `github.event.before`, the tip of `main` before the push. Unset, it uses the merge base with `origin/main`, or with a local `main`.

## Plug a product in

A product keeps its inventories under `products/<name>/` and names them in its own `harness.config.ts`. [Meridian's config](../../products/meridian/harness.config.ts) and [Nook's config](../../products/nook/harness.config.ts) are the two working examples.

1. Put the product under `products/<name>/`: its inputs, UX rules, catalog, chrome layouts, content layouts, page types, flows, features, stylesheet, and the `index.html` that `check:target-size` and `check:accessible-names` build. Beside each flow's `views` module, an `accessible-names.ts` says what a screen reader hears on each of the flow's previews.
2. Write `products/<name>/harness.config.ts`. Keep it plain literals, because `check:inventories` reads it at the pull request base with `git show`, where it cannot run imports. Paths in it are relative to the repository root. Type it with `satisfies HarnessConfig`, imported from `@agent-design-loop/harness`.
3. Name the design system adapter in the config's `adapter` field. A Todae product names `packages/adapter-todae/index.ts`.
4. First merge a proposal under `proposals/` that lists the product's directory under `changes`, such as `products/nook`, and get it approved as `status: decided`. The pull request that adds the product marks it `status: adopted`. The base has neither the product's config nor its inputs, so `check:inventories` reads it as a new product, and a new product needs an adopted proposal like any other membership change. Nook's first pull request added proposal 0005, before a proposal had to be decided first.
5. Add a `check:<name>` script that runs `npm run check:product -- --config products/<name>/harness.config.ts`, and add it to `check`, as `check:meridian` and `check:nook` are.
6. Add a CI job that runs `check:product` on the config and sets `INVENTORY_BASE`, as the `nook` job in `.github/workflows/ci.yml` does.

The config has four parts, and an optional fifth. `HarnessConfig` in `src/lib/parse-config.ts` documents each field.

| Field | What it names |
| --- | --- |
| `adapter` | The design system adapter module |
| `paths` | `source`, `features`, `layouts`, `contentLayouts`, `pageTypes`, `catalog`, `inputs`, `rules`, `styles`, `app`, and `web`: where each inventory and the product UI live |
| `shells` | `primarySlots`, the page types whose shell holds one primary action, and `collections`, the page types that are collections, with their chrome slots. Every slot named must be one the shell defines as `Object.assign(Root, { ... })` |
| `flows` | Each flow's `states` and `views` modules, its `tasks` mapped to task graph modules, and its `previews` |
| `optOuts` | Optional. The harness rules this product does not follow, each mapped to the decided proposal that says why. `paths.proposals`, also optional, is the folder an opt-out's proposal must sit in, `proposals` by default. Changing it is a config path change, so `check:inventories` asks for a proposal, and that check reads proposals from this folder |

`CODEOWNERS` already asks for review on `/products/*/harness.config.ts`, `/proposals/` and any other folder named `proposals`, `/packages/harness/`, `/packages/adapter-todae/`, and `/.github/workflows/`. Changing a config path can empty a check, so a config change needs a proposal and that review.

## Use it as a testing ground

1. Give an agent a UI task that is already in the product's inputs, such as `products/meridian/inputs/product.ts`. Do not invent a task, a layout, a content layout, or a page type in the same change.
2. The agent reads the inventories: product inputs, UX rules, the catalog, layouts, content layouts, page types, and the flow. `AGENTS.md` is only the pointer. It does not list what those inventories contain.
3. The agent runs the checks and fixes exit codes: a second primary, a raw control, a skipped state, a path over the budget, a layout, content layout, or page type that is not in the allowlist, or a collection body that is not a registered content layout.
4. Once the checks pass, the agent captures each state the change touches with `npm run screenshots`, into `products/<name>/review/screenshots/<change>/` with a gallery `README.md`, commits it, pins each image's link to its raw file at that commit with `--pin`, and links the gallery from the pull request. [Screenshots](docs/how-it-works.md#screenshots) has the command.
5. What the checks cannot decide goes in the product's `review/` folder as a short note. Meridian's notes are in `products/meridian/review/`.
6. If a rule has to break, or the work needs a catalog export, layout, content layout, page type, flow state, or rule input that is not already recorded, the agent adds a file under `proposals/` with a reason, a preview, and an adoption. It does not invent the missing piece, and it does not edit the inventory to sneak the change through. The inventory check fails that membership change until a designer has approved the proposal on main, as `status: decided`, and the change marks it `status: adopted`. A change that only adds catalog exports, layouts, content layouts or flow states may instead adopt a proposal it adds, listing them under `adds`, in the one pull request a designer reviews. A new page type always takes two pull requests, because it also needs an entry under `shells` in the product's config.

## Proposals

A proposal is how an inventory grows. [proposals/README.md](../../proposals/README.md) lists the inventories and what a proposal file must contain.

When a designer approves a proposal, a reviewed pull request moves it to `status: decided`. A later change adopts it into the inventory data and the checks: the catalog, a layout, a content layout, a page-type shell, the flow model, or the product inputs, and marks it `status: adopted`. The next run is constrained by that change. The inventory check reads the decided proposal from the base, so it refuses a change that adopts the proposal its own pull request adds, except an addition whose proposal lists only `adds` ([proposal 0012](../../proposals/0012-additions-in-one-pull-request.md)). A proposal that changes no inventory, such as [proposal 0011](../../proposals/0011-proposal-fields-and-graduation.md), may start as `adopted`.

## Rules apply to every product

A rule is a check that `check:rules` runs. An approved pattern is adopted straight into the harness as one of those, so it applies to every product from the pull request that adds it. A product that should not follow a rule opts out by adopting a decided proposal, a rule leaves `check:rules` only by adopting one that retires it, and a rule most products opt out of is flagged for retirement, so the harness can shrink as well as grow. [How a pattern becomes a rule](docs/how-it-works.md#how-a-pattern-becomes-a-rule) walks the lifecycle, and [proposals/README.md](../../proposals/README.md#opting-a-product-out-of-a-rule) gives the opt-out format.

## The design system adapter

The checks hold no design system names of their own. They read them from the adapter module the product's config names: the design system's packages, its action control and which variant is primary, its disclosure, its question part, the status pieces a page shell may hold, and the tokens behind the action control's size. `DesignSystemAdapter` in `src/lib/adapter.ts` is the type.

Todae's adapter is its own package, [`@agent-design-loop/adapter-todae`](../adapter-todae/index.ts), at `packages/adapter-todae/index.ts`. It names `Button.Root`, `Disclosure.Root`, `Disclosure.Summary`, and `Field.Root`. Like the config, it stays plain literals, and a change to it needs a proposal. `fixtures/fake-ds/` is a stand-in design system with its own adapter, and the checks must pass it.

## The package entry

A product imports the harness by its package name, `@agent-design-loop/harness`. The root `package.json` declares `packages/*` as npm workspaces. `index.ts` exports:

- `HarnessConfig`, `ShellRules`, and `FlowConfig`, the config types a product's `harness.config.ts` satisfies
- `DesignSystemAdapter`, the type an adapter satisfies
- `shortestPath`, `eventEdges`, and `TaskEdge`, the path search a product's task graphs use, and `measureRoutes`, which measures every route to a task's success against its budget

It exports only types from the adapter module, because loading that module runs a check's config read.
