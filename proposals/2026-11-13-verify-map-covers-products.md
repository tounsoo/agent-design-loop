# The verify map covers every page, block, task and scenario

Decided by Ben on Nov 13, 2026, in his answer to that evening's agent review ("Both"): turn his rule that a pull request that adds a page, a section or a check updates `CLAUDE.md` and the verify skill in the same pull request into a check, because the rule slipped on PRs 67 and 69. It changes the harness's own repository check, `check:docs`, not an inventory, and no rule in `check:rules`, so it lists no changes and is adopted in the pull request that makes it.

Rule or input: `check:docs` already fails a stale check list in `CLAUDE.md` and the verify skill, so a check could not land undocumented. It gains three parts.

- **Generated by construction.** `npm run docs:gen` writes a list of every product into `CLAUDE.md`, with each product's page types and their kinds, layouts, content layouts and tasks, and into the verify map's index, with how many of each and how many scenarios, read from the product registry. Scenarios are counted only in the map's index, so adding one, which needs no proposal, needs no edit to `CLAUDE.md`. It writes the verify skill's browser drive too: each Chrome rule check, in `check:rules` order, on each product. A new product, page type, layout, content layout, task, or Chrome rule check changes those blocks, so `check:docs` fails until `docs:gen` runs, and nobody edits the lists by hand.
- **One folder per product.** The verify map, `.claude/skills/verify/features/`, gains a folder per product, named after the product's own folder, with a `README.md` that links each feature file. Meridian's files move into `meridian/`, and Nook, which had none, gets its own. `check:docs` fails a product with no folder, a folder that is no product's, two products whose folders share a name, an index that misses a feature file or links one that is not there, a Markdown file below a product's folder, where it would not be read, and a page at the top of the map that the map's own index does not link, such as a recipe left there from before the folders.
- **Covers, both ways.** Each feature file ends with `## Covers`, which names, in code spans, the page types, layouts, content layouts, tasks and scenarios it drives, a scenario as `?scenario=<id>`. `check:docs` fails a page type, layout, content layout, task or scenario of a product that none of its feature files covers, a `Covers` line naming one the product no longer has, a second `## Covers` or a heading after it, and a `?scenario=` URL anywhere in the folder, code blocks included, that opens no scenario of that product. `docs:gen` never writes a feature file, so it cannot paper over a gap: the recipe is hand-written.

Construction comes first, as the Nov 12 rule asks: whatever can be written from the code is generated, and the check holds only what can't, the recipe that says how to reach and drive each part.

## Reason

The rule lived in thread briefs and in `CLAUDE.md`'s conventions, and only the check list was enforced. PR 69 added the vendor page, a new `profile` page type and the `invoice-list` content layout, and neither `CLAUDE.md` nor the verify skill named them. PR 67 changed `check:rendered-page` from heading sizes to heading structure, and the verify skill's step 3 still described "section headings two type-scale steps below the title". Nook had no verify map at all, and the skill's browser drive ran the Chrome checks on Meridian only.

A section, in Ben's words, is a block on a page, and every block on a page is a registered content layout since [proposal 2026-11-13-page-bodies-from-content-layouts](2026-11-13-page-bodies-from-content-layouts.md). So the registry already names every page and section a product has: its page types and its content layouts, with its layouts, tasks and scenarios around them. Holding the map to that registry is structural, not a text search for prose: the check reads names from code spans in one labelled section, and the names from the config, the folders and `scenarios.ts`.

What it cannot see: whether the recipe above a `Covers` line drives what it names, which stays the reviewer's to judge; a new page built only from a page type and content layouts the product already has, with no new scenario, such as a fourth Meridian collection, because the registry names page types, not pages; a section added inside an existing content layout, or a new step or control on an existing page, which adds no name; and anything in the verify skill's hand-written prose, such as a check's description going stale, beyond the generated blocks. Those are left to review and to the critique.

## Preview

A pull request that adds a content page type `receipt` to Meridian, with a `receipt` scenario, and no recipe, before `npm run docs:gen` has run:

```text
docs: CLAUDE.md, .claude/skills/verify/features/README.md are stale. Run npm run docs:gen.
docs: the verify map in .claude/skills/verify/features/ misses what the products have:
- meridian's page type `receipt` is in no feature file of its verify map. Say how to reach and drive it in a feature file under .claude/skills/verify/features/meridian/, and name it as `receipt` on its "- Page types:" line under ## Covers.
- meridian's scenario `receipt` is in no feature file of its verify map. Say how to reach and drive it in a feature file under .claude/skills/verify/features/meridian/, and name it as `?scenario=receipt` on its "- Scenarios:" line under ## Covers.
```

After `npm run docs:gen`, the first line goes and the map's lines stay until the recipe is written. With the map up to date, `npm run check:docs` ends:

```text
docs: 5 docs describe 25 scripts, 148 fixture cases and 2 products, as the code has them.
docs: the verify map covers 5 page types, 2 layouts, 11 content layouts, 3 tasks and 29 scenarios of 2 products, and nothing they lack.
```

## Adoption

Nothing changes later. These change in the same pull request:

- `packages/harness/src/lib/verify-map.ts`, with its tests, reads the registry and the map; `check-docs.ts` runs it, and `lib/docs.ts` writes the new generated blocks.
- `check-docs.meta.ts` says what the check now fails, and `npm run docs:gen` rewrites the check reference, `CLAUDE.md`, the harness README, the verify skill and the map's index.
- The verify map moves Meridian's files into `meridian/`, adds the vendor page's, and gives Nook its own folder, each feature file with its `## Covers`.
- `CLAUDE.md` and the verify skill say how the map is held, and the skill's step 3 describes `check:rendered-page` by heading structure, as proposal 2026-11-12-heading-structure made it.
