# Claude instructions

This repository tests whether an agent designs better UI when the rules live in the repo as data and as checks that fail the build. The sample product is **Meridian**, an accounts-payable workspace built on [Todae](https://github.com/tounsoo/todae) through one catalog file. [`AGENTS.md`](AGENTS.md) is the design loop every agent follows, Claude included: read it, and the inventories it lists in order, before changing UI. The loop itself is a graph in [`packages/harness/design-loop.ts`](packages/harness/design-loop.ts): follow its nodes and edges from `start`. [`packages/harness/docs/how-it-works.md`](packages/harness/docs/how-it-works.md) is the walkthrough for people new to the repo, and [`products/meridian/README.md`](products/meridian/README.md) covers Meridian.

## pstack

Work here uses [pstack-claude](https://github.com/michael-denyer/pstack-claude). A local Claude Code session gets the `pstack` plugin from `.claude/settings.json` once the folder is trusted, and its SessionStart hook routes tasks to poteto-mode.

Claude Duet threads: read [`.claude/thread-start.md`](.claude/thread-start.md) next. A thread attaches the repository after it starts, so no SessionStart hook fires and nothing in `.claude/` loads by itself. That page installs pstack by hand.

The model sheet is [`.claude/pstack-models.md`](.claude/pstack-models.md), pstack's project sheet. It names Opus, Sonnet and Haiku only. No Fable.

## Set up

Node 22, the version CI runs (`engines` asks for 22 or newer). Install with `npm ci`, then `npm run setup:chrome` for the headless Chrome `check:target-size`, `check:accessible-names` and thirteen fixture cases run in. `.npmrc` sets `legacy-peer-deps`.

## Commands

The build gate. CI runs the same checks, split into one job per product:

```sh
npm run check:fixtures && npm run check
```

- `check:fixtures` runs the harness's own tests. `packages/harness/fixtures/product/` is a small product with its own `harness.config.ts` that every check passes. Every other folder directly under `packages/harness/fixtures/` or its `illegal/` is a case whose `case.ts` changes some of that config's paths and names the checks to run on it, each as its npm script with `--config`. It passes only when every illegal case fails with its expected message and every legal case passes with its expected message. A folder with no `case.ts` fails the run. A case that sets `base` may also give `proposals` and `baseProposals`, folders `check:inventories` reads as the change's proposals and the base's. Thirteen cases build their own page, or reuse another case's, and open it, so like `check:target-size` and `check:accessible-names` the run needs Chrome. `npm run check:fixtures -- illegal/two-primaries` runs one case.
- `check` runs typecheck, ESLint and the Vitest suite on the whole repository, then `check:product` on Meridian's config and on Nook's, then `check:proposals`, then `check:retirement`, then `check:loop`. `check:product` first runs `check:opt-outs`, then every rule check in `check:rules`: off-catalog UI, detail slots, step budget (every route that finishes a task, not only the shortest, must fit its `max_steps`), disclosure, priority, one-thing, inventories, state coverage, target size and accessible names, in that order. It skips a rule the product opts out of in its config's `optOuts`. Each rule check needs `--config <product config>`; there is no config at the root. The harness README's "Run the checks" table says what each one fails.
- `check:proposals` takes no `--config`. Every proposal starts with front matter, `status` (`open`, `decided` or `adopted`) and `changes` (the exact inventory names it changes, or `[]`), with optional `retires`, `opts-out`, `adds` and `tightens` lists, then `## Reason`, `## Preview` and `## Adoption` sections with text, not the names before the rename (`status: graduated`, `## Graduation`), which only a base proposal may still have. A proposal that lists anything under `changes` or `adds` also has a `## States` section: `- <state>: <text>` items naming at least one ordinary state and each edge case (Empty, Loading, Error, Long content, Permissions, Over time), described or written `Out of scope, <why>`, or the one item `- None: <why>`. It fails a file without them, `adds` or `tightens` beside `changes`, `retires` or `opts-out` or on a proposal that is not `adopted`, and, compared with the base, a status that moves more than one step or backwards, a decided or adopted proposal whose lists change, a decided or adopted proposal renamed or deleted, a new proposal that starts `adopted` while it lists anything but `adds` or `tightens`, a proposal that changes or adds members with no `## States` when it is new or moves `open` to `decided`, a decided or adopted proposal that drops the `## States` it had, and a proposal the change adds or renames whose file name is not a real date no later than tomorrow in UTC, the day it was written, and a lowercase slug, such as `2026-11-12-side-panel.md`, or that shares its name with a proposal in another proposal folder. The proposals that merged with a number, from 0001, keep those names. Proposals already on the base keep their text, without `## States`, until they move to `decided` ([proposal 2026-11-11-proposals-list-every-state](proposals/2026-11-11-proposals-list-every-state.md)). `proposals/README.md` has the format.
- `check:opt-outs` fails an opt-out that has no adopted proposal directly in the product's `paths.proposals` folder (`proposals/` by default) listing `<rule> for <paths.source>` under `opts-out`, or that names a rule outside `check:rules`. Off-catalog UI and inventories cannot be opted out. `check:retirement` takes no `--config`: it reads every product's `harness.config.ts`, checks their opt-outs, and fails when a majority of products, and at least two, opt out of the same rule. Compared with the base, it also fails a rule that leaves `check:rules`, or a new opt-out, unless the change adopts a proposal decided on the base that lists it under `retires` or `opts-out`. [Proposal 0008](proposals/0008-rule-opt-out-and-retirement.md) and [proposal 0011](proposals/0011-proposal-fields-and-graduation.md) have the rules.
- `check:loop` takes no `--config`. It fails when the design loop graph in `packages/harness/design-loop.ts` has a dangling edge or unreachable node, an eval node that names a missing script or has no retry on `fail`, a human gate with no `CODEOWNERS` owner, or an end the run can reach without an eval node passing after the last change, and when the diagram in `packages/harness/docs/how-it-works.md` is stale. `npm run check:loop -- --write` redraws the diagram. [Proposal 0009](proposals/0009-design-loop-graph.md) records the graph.
- `check:trace` takes no `--config`. It reads the change against its base, as `check:inventories` does, and fails when the change touches a product's directory and adds no loop trace under `traces/`, or when a trace it adds or edits is not a walk of the design loop graph that stops at a checkpoint, with the gate passed after the last change when that checkpoint ends the run. It is not in `check`, because the gate runs in the middle of the walk: CI runs it after `check:loop`, and an agent runs it before pushing. `npm run loop:step -- traces/<change>.jsonl <node> [when]` appends a step and refuses one the graph does not allow. [Proposal 0010](proposals/0010-loop-trace.md) records it, and says why a trace is a record, not proof.
- `check:target-size` builds the product's app, serves it with `vite preview` on port 4173 and measures controls in headless Chrome. It finds Chrome at `CHROME_PATH`, then the chrome-headless-shell that `npm run setup:chrome` installs into `.cache/chrome` (the build `puppeteer-core` pins; CI runs the same script), then the usual `/usr/bin` paths. Without one it fails, naming where it looked and both fixes.
- `check:accessible-names` builds and serves the app the same way and reads Chrome's accessibility tree on each preview. Beside each flow's `views` module, `accessible-names.ts` exports `accessibleNames` (`satisfies AccessibleNames`): each preview mapped to what a screen reader should hear there, as a role with a name or text and any states. It fails a control with no accessible name, a declared announcement the page does not make, a node with `aria-current` (declared with its `current`), a live region (a live role or `aria-live`) with something to say, or a progress bar or meter that the file leaves out, and a missing file, a preview it declares nothing for or a key that is not a preview. Declare what changes between states, not the whole tree. Then it presses each enabled button, link, disclosure summary, menu item, tab, checkbox, radio or switch on each preview, one per fresh load with the page's storage cleared, with Enter or Space, reads the page 150 ms later, past the delay of Todae's announcer, and fails a press that changes what a screen reader could read without saying so (no live region says anything new, focus does not move, and the control's own expanded, checked, pressed or selected state does not change), and a press after which focus is on the page body. A press that loads another document is skipped and not counted. The same file may export `knownGaps` (`satisfies KnownGaps`), press problems a product has not fixed yet, each with its presses as the failure names them, its problem (`"silent"` or `"focus lost"`), the previews it happens on (leave them out to cover every preview, later ones included), why it waits, and `fixIn`, the GitHub issue or pull request URL or the proposal file its fix waits on: a listed problem passes, an entry whose press no longer has its problem on a preview it names fails, so the list only shrinks, and an entry with no `fixIn`, or one naming a proposal file that does not exist, fails. `--list` checks the file without Chrome. Each product's shell moves focus to the new page's h1 on a page change, and a submit that turns itself off uses the catalog's `submitOff` (`aria-disabled`, not `disabled`) so it keeps focus; a press problem those cover is fixed there, not listed. [Proposal 2026-11-11-accessible-names-per-state](proposals/2026-11-11-accessible-names-per-state.md), [proposal 2026-11-12-press-every-action](proposals/2026-11-12-press-every-action.md) and [proposal 2026-11-12-shell-owned-focus](proposals/2026-11-12-shell-owned-focus.md) have the rule.
- `check:inventories` and `check:trace` compare with `INVENTORY_BASE` when set. CI sets it to the pull request base, or on a push to `main` to `github.event.before`, the tip of `main` before the push. Unset, it uses the merge base with `origin/main`, or with a local `main`. A membership change passes only when it adopts a proposal: `status: decided` on the base, `status: adopted` in the change, with what changed listed under `changes` on the base. It reads a list only when the file exports it by name, with `export const` or an export clause over a local `const`, and a base file with `export *` or `export =` that does not export a list by name fails, so a re-export cannot pass for a missing list. It compares item by item ([proposal 2026-11-12-right-size-governance](proposals/2026-11-12-right-size-governance.md)). A change that only adds or only tightens takes one pull request: it passes with a proposal the change adds, `status: adopted`, that lists under `adds` each new member of the catalog exports, `allowed_layouts`, `allowed_content_layouts` or the flow states by its bare name, `page-type:<id>` for a new page type with its own new `shells` entry (every entry the base had unchanged; it prints the rule and slots the page type joins), `task:<id>` for a new task with its graph module, and `preview:<state>?<query>` for a new preview pair, and under `tightens` `max_steps:<task id>` lowered, a cap lowered, `TARGET_MIN_PX` raised, or `disclosed_sections:<section>` added. Such a proposal covers nothing once it is on the base, when one of its `adds` is a name the change removes or changes otherwise, when one of its `tightens` loosens, when the change moves any tightenable input the other way, or when a base proposal already lists one of its `adds` for the same list. Anything else, a removal, a rename, a loosening, a `success_state`, `priority`, a config path, a `shells` entry the base had, any other `flows` change, the adapter or a new product, takes two pull requests, decision then adoption ([proposal 0011](proposals/0011-proposal-fields-and-graduation.md)). The approval is the code owner's merge: Ben, in this repository. Under `--base`, a fixture compares no config, but a new page type still reads both configs' shells. `shells.collections` that names every slot of a shell as chrome fails, since its pages would have no body slot.

`npm run screenshots -- --config <product config> --out products/<name>/review/screenshots/<change> --base origin/main [--state <state>]` is the design loop's `screenshots` step, not a check: once the gate passes, it captures the previews `check:target-size` opens, at 1280 by 900 in the same Chrome, before and after, and writes a gallery `README.md` whose images each link to their own file. Commit the folder, then run `npm run screenshots -- --config <product config> --pin <folder>`: it points each image's link at the raw PNG on `raw.githubusercontent.com` at that commit, so a click opens the image itself, full size on a phone too, rather than GitHub's page for the file, and it refuses a folder with anything but its `README.md` uncommitted. Commit the `README.md` again and put the line `--pin` prints, a plain link to the gallery with `<sha>` replaced by the pushed commit's full SHA, in the pull request description, with its whole `https://github.com/` address, since a relative path breaks in the GitHub app and in email, and a branch link breaks once the branch is deleted; images in the description itself don't come through from an agent. [Proposal 2026-11-11-screenshot-gallery](proposals/2026-11-11-screenshot-gallery.md) records it.

Others: `npm run dev` starts Meridian on Vite's port and `npm run dev:nook` starts Nook; `npm run build` and `npm run preview` serve Meridian's built app.

## Verify

Prove every change with [`.claude/skills/verify/SKILL.md`](.claude/skills/verify/SKILL.md). It runs the build gate, then drives the surface the change touches, and ends in PASS, FAIL or BLOCKED.

## Conventions

- Follow the loop in `AGENTS.md`. Import UI only from the product's catalog, `products/meridian/catalog/index.ts` for Meridian. A missing catalog export, layout, content layout, page type, flow state or rule input is a proposal under `proposals/`, never an edit to an inventory. The inventory edit waits for a later pull request, once the proposal is decided on the change's base (`main` for a pull request into `main`), unless it only adds or tightens: then a proposal that lists it under `adds` or `tightens` is adopted with it, and a new page type with its own `shells` entry goes under `adds` as `page-type:<id>` (`proposals/README.md`).
- Agents don't merge, delete branches, force-push or rebase without Ben's yes.
- Push only once the build gate and an internal review are green. Draft pull requests are fine; mark one ready once its CI is green.
- A pull request that adds or changes a check also updates `CLAUDE.md` and the verify skill in `.claude/skills/verify/SKILL.md` in the same pull request, so neither describes a check that no longer exists. Ben gave that standing yes on 2026-11-11.
- Change `CLAUDE.md` and anything in `.claude/` only with Ben's yes. Leave Cursor's own config alone.
- Where these docs and the code disagree, follow the code and say so in the pull request.
